# 向导式两步流 四层设计（v1.3：两个功能融合为一条主线）

> 本质锚定：①测我的调与②哼唱翻译从来不是并列的两个功能，而是同一条主线的前后两步——先"认识你的嗓音"（找到你的 do），再"用你的调读音乐"（哼唱翻译）。分裂感来自 UI 把它们摆成两张并列卡片、衔接逻辑藏在按钮流程里。融合 = 叙事统一 + 状态上浮 + 自动衔接。

## 反常识根因（设计依据）

> 融合不等于合并。把两卡拼成一张、一个按钮全自动串联（强制顺序、灵活性低）反而违背工具本质——用户经常只想要其中一个能力。正确的融合是**信息流接通**：第①步的产出（do）自动成为第②步的输入，但每一步都可独立使用、独立重做、可跳过。

## 四层设计

| 层面 | 设计 |
|---|---|
| **数据规矩** | 全局档案三字段：`myKey`（固定调，localStorage）、`lastRange`（音域，会话态）、`lastResult`（最近一次哼唱分析，会话态）；每步完成态 = myKey 存在 / lastResult 存在 |
| **数据存储** | myKey → localStorage（v1.1.1 MyKeyStore 复用）；音域与会话结果仅内存，页面关闭即销毁（隐私铁律不破） |
| **数据流转** | 状态条常驻顶部（我的调 + 音域 + 清除）；第①步音阶定调成功 → 主按钮「✓ 就用它（X 大调），去哼歌 →」= 设调 + 存储 + 同步 + `gotoHum()`（smooth 滚动 + flash 动画）；滑音模式点推荐主音后同样亮出衔接按钮；第②步结果行标注「★ 按第①步找到的 do（X 大调）翻译」，未固定时「自动猜调（做完第①步就不猜了）」 |
| **数据接口** | `gotoHum()`（interfaces 内部）；`syncMyKeyUi()` 扩展（状态条 + 步骤✓标记）；HTML 新增 `#status-bar / #status-my-key / #status-range / #status-clear / #cal-done / #hum-done`；domain/application **零改动**（纯 interfaces 层重排） |

## 交互规则

- 两卡标题改步骤叙事：`第 ① 步 · 找到你的 do` / `第 ② 步 · 用你的调哼唱`，完成后标题旁亮 ✓ 徽标
- 每步可独立重做；跳过第①步直接哼唱仍可用（自动猜调），hint 明说"没做过第①步也能用"
- 钢琴区保留「★ 记住当前调」（第②步修正后更新固定调的入口）；「清除」上浮到状态条，避免两处重复

## 验证

- I：30/30 回归保持绿、TSC-CLEAN、build 通过（纯 UI 重排，判定逻辑零改动）
- Q（人工）：状态条随固定/清除即时更新；音阶定调后点击主按钮滚动到第②步并闪烁；滑音点主音后亮出"去哼歌"；两步✓标记正确
