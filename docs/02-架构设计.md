# 找调儿 FindMyKey 架构设计

## 1. 架构总览

分层职责表（依赖自上而下单向，禁止反向）：

| 层 | 目录 | 职责 | 可依赖 |
|---|---|---|---|
| 数据接口 | `src/interfaces/`、`index.html` | 事件绑定、结果渲染（音域图/唱名时间线/调性选择）、实时音高画布 | application, runtime |
| 运行时 | `src/runtime/engine.ts` | AudioContext/Worklet 生命周期、消息泵、重采样、缓冲回收 | infrastructure, core |
| 流转-编排 | `src/application/session.ts` | 分析会话状态机、三大用例（校准/翻译/演示）、主音切换重映射 | domain, core |
| 流转-规则 | `src/domain/*.ts` | 纯算法：yin / pitch-track / segment / tonality / solfege / voice-range | core |
| 数据存储 | `src/infrastructure/capture-worklet.js` | worklet 线程内采样缓冲（512 样本分帧）→ postMessage | 无（自包含） |
| 数据规范 | `src/core/*.ts` | types / constants / errors / synth（离线合成器，测试与演示共用） | 无 |

数据流（一次"哼唱翻译"）：

```
麦克风 → getUserMedia(关闭 AGC/NS/回声消除)
      → AudioWorklet(16kHz, 512样本/帧, transferable postMessage)   [事件循环]
      → runtime 消息泵累积缓冲（同时喂给 LivePitcher 供校准实时显示）
      → stop(): 拼接为 Float32Array(16k, mono)                      [空间移交]
      → application.analyzeRecording(buf)                           [顺序管道]
          domain.trackPitch   → F0 帧(中值滤波+八度纠错)
          domain.segmentNotes → Note[](起止/中位MIDI/音分偏差)
          domain.inferKey     → KeyCandidate[](覆盖率+KS相关性+首尾音锚定)
          domain.toSolfege    → SolfegeNote[](简谱数字+变化音+八度点)
      → interfaces 渲染（唱名时间线 / 调性选择器 / 音分提示）
```

## 2. 技术选型理由（由本质与时空需求推导）

| 决策项 | 选择 | 推导逻辑（回溯本质） |
|-------|------|---------------------|
| 形态 | Web 单页 | 翻译器的本质要求"零安装、随手可用"——摩擦最小化；麦克风权限与 Web Audio 已足够 |
| 语言 | TypeScript（strict） | 规则契约要求编译时拦截：DTO 形状、值域枚举、纯函数签名即契约 |
| 采集 | AudioWorklet 而非 ScriptProcessor | ScriptProcessor 已废弃且主线程卡顿破坏时间确定性；Worklet 独立线程 + transferable 零拷贝 |
| 采样率 | 统一 16kHz（AudioContext 选项） | 人声 F0 ≤ 1kHz，16kHz 完全够用且让 YIN 每帧计算量减半；离线测试与在线运行共用同一时基 |
| 音高算法 | YIN 自实现，不用深度模型 | **反常识根因**（见 §4）：哼唱识别的信号是"形状"不是"音色"，经典 DSP 90 分即可，深度模型是伪需求 |
| 调性算法 | 音阶覆盖率 + Krumhansl-Kessler 画像相关性 + 首尾音锚定 | 短旋律的调性是病态问题（相对大小调二义性），锚定启发式比重型模型更可控、可解释、可测 |
| 测试 | vitest + 离线合成器（core/synth） | I 不变量（纯函数可复现）要求测试不依赖麦克风；合成音频 = 可控真值 |
| 依赖策略 | 核心零运行时依赖 | 可审计（算法即文档）、可测试（无 mock）、无供应链风险 |

## 3. 运行时（时空管家）显式设计

`runtime/engine.ts` —— 唯一有状态生命周期模块：

| 钩子 | 职责 | 空间/时间语义 |
|------|------|-------------|
| `init()` | `new AudioContext({sampleRate:16000})` + `audioWorklet.addModule()` | 开辟全局空间（音频时钟与处理线程） |
| `start(hooks)` | getUserMedia（显式关闭 echoCancellation/noiseSuppression/autoGainControl，保真 F0）→ 建 AudioWorkletNode → 连接 → 启动消息泵 | 启动时间流；帧事件开始推送 |
| `stop()` | 断开节点 → 停止轨道 → 拼接缓冲（必要时线性重采样到 16k）→ 释放帧缓冲 | 时间流暂停；空间移交分析层 |
| `destroy()` | 按依赖逆序回收：node.disconnect → stream tracks.stop → `ctx.close()` → 置空引用 | 空间回收，防悬垂（I 不变量：无泄漏） |

worklet 内部：`CaptureProcessor` 累积 128 样本块 → 凑满 512 样本 → `postMessage`（transfer buffer）→ 主线程入队。录音上限 15s（约 469 帧，无性能压力）。

## 4. 设计依据（反常识根因）

> **反常识根因 1：哼唱识别不需要"AI 听懂音频"。**
> 直觉上识别哼唱 = 深度模型听音频。但首调唱名的同构性决定了：哼唱的**绝对音高是噪音**（整体漂移、八度漂移、男声哼女声歌自动降八度），**音程形状才是信号**。因此管线用经典 DSP（YIN）提取形状、用模板匹配（覆盖率+KS 相关性+首尾锚定）定主音，90 分效果、100 分可解释性与可测试性。深度模型只值得在"主音二义性兜底"出现真实痛点后再引入。

> **反常识根因 2：找 key 不是测"你最高能唱多高"。**
> 极限音域（能尖叫到多高）对选调几乎无用——唱歌用的是**舒适区**，且旋律重心偏音域中上部。因此音域测量对滑音轨迹做 3%/97% 百分位裁剪（去掉破音/假声切换毛刺），推荐主音区间按"do−5 半音 ≥ 舒适下限 且 do+9 半音 ≤ 舒适上限"计算（旋律典型跨度：do 上方最多到 la，下方最多到 sol）。

## 5. 关键常量（规范层，全部集中于 `core/constants.ts`）

| 常量 | 值 | 说明 |
|------|----|----|
| ANALYSIS_RATE | 16000 Hz | 统一分析采样率 |
| FRAME_SIZE / HOP | 1024 / 256 | 64ms 窗 / 16ms 步（≈62.5 帧/s），可检测 31–1000Hz |
| YIN_THRESHOLD | 0.12 | CMND 阈值 |
| 有声判定 | prob ≥ 0.5 且 rms ≥ max(0.004, 全局p95×0.06) | 自适应静音门限 |
| 音符切分 | 步进阈 0.8 半音；容忍静音 ≤2 帧；最短 80ms 且 ≥4 帧 | 抗颤音/抖动 |
| 调性打分 | 0.5×覆盖率 + 0.3×KS相关 + 0.2×锚定(0.7×尾音+0.3×首音) | 锚定：主音1/属音0.6/三音0.3 |
| 音域裁剪 | p3 / p97；跨度 <10 半音判"范围太小" | 去毛刺 |
| 推荐主音带 | do−5 ≥ 低限 且 do+9 ≤ 高限 | 旋律典型跨度启发式 |
